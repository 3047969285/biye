## 中文摘要

随着电力行业数字化转型的持续推进，传统依赖人工巡检与经验判断的运维模式已难以满足规模化电网的精细化管理需求。本文设计并实现了一套基于 Spring AI 的智能电网运维管理系统。系统采用前后端分离架构，后端基于 Spring Boot 3 与 Spring AI 框架集成阿里云通义大模型，前端采用 Vue 2 与 Element UI 构建交互界面，数据层使用 MySQL 与 MyBatis。系统主要包含六个功能模块：设备与多维运维数据管理、规则驱动的告警与状态联动、基于检索增强生成（RAG）的智能问答、运维表单自动编排与推送、风力发电功率预测（Java 调用 Python GRU 深度学习服务），以及基于业务主键去重的站内消息中心。测试结果表明，该系统在提升运维效率、降低人工压力以及辅助决策方面效果显著，具备工程可行性与一定的创新价值。

**关键词**：智能电网；运维管理；Spring AI；检索增强生成；风力发电预测

## Abstract

With the continuous advancement of digital transformation in the power industry, the traditional operation and maintenance mode relying on manual inspection and empirical judgment can no longer meet the refined management needs of large-scale power grids. This paper designs and implements an intelligent power grid operation and maintenance management system based on Spring AI. The system adopts a front-end and back-end separation architecture. The back-end integrates the Alibaba Cloud Tongyi large language model based on Spring Boot 3 and the Spring AI framework. The front-end uses Vue 2 and Element UI to build the interactive interface, and the data layer uses MySQL and MyBatis. The system mainly includes six functional modules: equipment and multi-dimensional operation data management, rule-driven alarm and status linkage, intelligent question answering based on retrieval-augmented generation (RAG), automatic maintenance form orchestration and notification, wind power forecasting (Java calling a Python GRU deep learning service), and an in-site message center with business-key-level deduplication. Test results show that the system has significant effects in improving operation and maintenance efficiency, reducing manual pressure, and assisting decision-making, and has engineering feasibility and certain innovative value.

**Keywords**: smart grid; operation and maintenance management; Spring AI; retrieval-augmented generation; wind power forecasting

## 1 绪论

### 1.1 研究背景与意义

电力系统是国民经济的基础命脉，其安全稳定运行直接关系到社会生产与居民生活。随着可再生能源大规模并网和用电负荷持续攀升，电网规模不断扩大，设备类型日趋多元，运维管理面临的挑战愈发突出。传统运维模式以人工巡检和定期维护为主，存在信息孤岛、响应滞后、经验依赖等固有缺陷，难以适应现代电网精细化管理的迫切需求[1]。

近年来，随着大数据、云计算和人工智能技术的蓬勃发展，智能运维（AIOps）概念逐渐向电力行业延伸。将 **大语言模型（LLM）** 与 **检索增强生成（RAG）** 等前沿技术引入电力设备运维，可显著提升故障诊断自动化程度和知识复用能力[2]。与此同时，风力发电在我国电力结构中的比重持续上升，风力功率预测对于电网调度优化具有重要价值[3]。

本文在此背景下，面向实际运维需求设计并实现了一套智能电网运维管理系统。系统将设备状态监测、告警联动、AI 智能问答与运维表单生成、风力功率预测等能力有机融合，构建从 **数据感知—异常检测—智能辅助—预测预警** 的闭环，具有重要的理论研究意义与工程应用价值。

### 1.2 国内外研究现状

在智能运维领域，国外研究起步较早。以 Google、Netflix 为代表的互联网企业较早将机器学习引入运维监控，形成 AIOps 理论体系。在电力行业，欧美国家的智能电网研究聚焦于 SCADA 系统集成、预测性维护和数字孪生等方向，已有较为成熟的商业化解决方案。

国内研究方面，近年来成果颇丰。王磊[2]提出了智能电网电力运行维护一体化建设方案，强调数据集成与流程协同；王艳[3]分析了智能电网调度中自动化运维技术的应用路径；王坤[4]重点研究了规则引擎与自动化调度的结合；杜婷婷[5]探讨了运维一体化的实现框架；曾光[6]研究了自动化运维技术在运维管理中的具体应用。然而，上述研究多聚焦于某一方面，**将大语言模型能力与传统运维管理系统深度融合** 的完整工程实践仍相对欠缺。

在关键技术层面：Spring AI 框架为 Java 生态提供了统一的大模型调用接口；RAG 技术弥补了通用大模型在垂直领域知识不足的缺陷；GRU（Gated Recurrent Unit）深度学习模型在时序预测任务中表现出色，已被广泛用于风力功率预测研究。

### 1.3 主要研究内容与论文组织

本文主要研究内容如下：

（1）设计并实现基于若依框架的设备全生命周期与多维运维数据管理功能。

（2）构建轻量级规则引擎，实现设备运行状态变更时的告警自动生成与状态联动回写。

（3）集成 Spring AI 与 RAG，实现电力运维领域的智能问答、知识库检索、自然语言查库以及运维表单 AI 辅助生成。

（4）设计基于 GRU 神经网络的风力功率预测服务（Python FastAPI），并通过 Java HTTP 桥接实现预测结果的调度与可视化。

（5）实现基于业务主键 `(user_id, msg_type, biz_id)` 语义去重的站内消息推送系统。

论文其余章节组织如下：第 2 章进行需求分析；第 3 章阐述总体设计；第 4 章详细介绍各模块实现；第 5 章给出系统测试结果；第 6 章总结并展望。

## 2 系统需求分析

### 2.1 功能需求分析

根据电力运维业务特点，系统功能需求可归纳为以下六个方面。

**（1）设备与运维数据管理需求**

系统需支持对电力设备主数据（设备编号、名称、类型、安装位置等）及关联业务数据的增删改查与导出。业务数据涵盖运行状态、设备参数、告警记录、故障记录、维护记录，以及机械、电气、环境、经济、技术、气候等多维度子表数据。设备删除应支持级联清理关联数据；同时需提供首页数据聚合接口，支撑运维看板展示。

**（2）规则与告警联动需求**

运维人员需能为每台设备配置监测规则（参数名称、比较类型、阈值、严重级别等）。当运行状态记录新增或更新时，系统须自动执行规则匹配，将命中结果写入告警记录，并综合所有命中规则的严重程度回写运行状态（如将状态从"正常"升级为"警告"或"错误"），同时更新"是否需要维护"标志。同规则的重复告警应予去重。

**（3）智能问答与知识库需求**

系统需提供基于运维领域知识的 AI 对话，支持普通对话与 RAG 增强两种模式，均支持流式（SSE）输出。知识库文档须可上传、切分、入库，并可随时清空重建。还需支持自然语言转 SQL 查询，执行结果附带中文摘要。所有对话记录可持久化保存并查询。

**（4）运维表单需求**

系统需能从当前需维护设备列表出发，按设备聚合状态、故障、告警等多源信息，调用大模型生成标准化运维表单（包含维护类型、优先级、故障描述、步骤、安全注意事项等字段），支持单台与批量生成、入库、修改与删除。批量生成结果应以可切换列表展示。

**（5）风力发电功率预测需求**

系统需对接本地 Python 预测服务，支持全局预测与按设备预测两种模式。预测所需特征/功率 Excel 文件应支持上传与下载，并可通过页面编辑风速—功率序列代替文件。系统须按设备隔离数据，避免不同设备共用同一份演示文件。预测结果需以折线图形式展示，并可生成中文运维总结。

**（6）消息推送需求**

系统需在运维表单创建或设备进入待维护状态时，向相关用户推送站内消息，消息须按业务主键语义去重，避免重复打扰。

### 2.2 非功能需求分析

**安全性**：所有业务接口须登录鉴权；自然语言查库限制只读；风力预测接口绑定权限标识 `power:forecast:list`；关键操作记录操作日志。

**可靠性**：AI 调用失败时有规则化降级策略，保证核心功能可用；消息推送失败时有重试与日志告警机制。

**可维护性**：采用分层分模块设计，各功能独立，便于扩展与单独替换。

**性能**：首屏设备列表加载关闭 AI 摘要（`aiSummary=false`），减少首屏响应时间；预测结果在内存中按设备缓存，`/latest` 接口可快速读取，`live=true` 时才触发同步预测。

```sql
  device_name   VARCHAR(128) NOT NULL COMMENT '设备名称',
  device_type   VARCHAR(64)  NULL COMMENT '设备类型',
  install_loc   VARCHAR(200) NULL COMMENT '安装位置',
  status        TINYINT DEFAULT 1 COMMENT '状态 1正常 0停用',
  PRIMARY KEY (device_id),
  UNIQUE KEY uk_device_no (device_no)
) ENGINE=InnoDB COMMENT='设备主数据';
```

## 4 系统详细设计与实现

### 4.1 设备与运维数据管理模块

#### 4.1.1 模块设计

设备与运维数据管理模块遵循若依框架的标准分层架构：**Controller → Service → Mapper → XML**。设备相关接口统一置于 `/equipment/*` 路径，权限前缀为 `equipment:*`，通过 `@PreAuthorize("@ss.hasPermi('equipment:device:list')")` 等注解实现接口级访问控制。

#### 4.1.2 级联删除实现

为保证数据引用一致性，设备删除操作需按依赖顺序清理 10 余张子表数据。在 `EqDeviceServiceImpl` 中通过事务注解 `@Transactional` 包裹，按以下顺序执行：

```
告警记录 → 故障记录 → 维护记录 → 运行状态 → 规则 →
电气/机械/环境/经济等子表 → 设备统计 → 设备主表
```

这样可确保即使某一步失败，整个删除操作也会回滚，不留脏数据。

#### 4.1.3 多维数据展示

首页/看板接口返回的聚合数据包含：设备总数、各运行状态数量分布（正常/警告/错误/离线）、近期告警趋势、待维护设备数等。该接口通过多条聚合 SQL 合并后，以 Map 结构统一返回，前端基于 ECharts 进行可视化展示。

### 4.2 设备规则与告警联动模块

#### 4.2.1 规则引擎设计

规则引擎采用轻量自研方式，不依赖 Drools 等重型框架，核心接口为 `IEqDeviceRuleTriggerService`。规则支持以下比较类型：大于（`>`）、小于（`<`）、等于（`=`）、大于等于（`>=`）、小于等于（`<=`）、区间（`BETWEEN`）。规则配置存储于 `eq_device_rule` 表，包含参数别名 `param_alias`（对应运行状态记录中的测点字段）、比较类型、阈值和告警级别。

规则匹配核心逻辑如下：

```java
// 伪代码示意
for (EqDeviceRule rule : enabledRules) {
    Object value = getFieldValue(status, rule.getParamAlias());
    if (value != null && matches(value, rule)) {
        // 去重：同规则同设备若已有 status=0（未处理）的告警则跳过
        if (!alertRecordMapper.existsUnprocessed(deviceId, rule.getRuleId())) {
            alertRecordMapper.insert(buildAlert(rule, deviceId));
        }
    }
}
```

#### 4.2.2 评估结果回写

规则评估编排服务 `IEqDeviceRuleEvaluationService` 在触发完整评估后，将所有命中规则的结果汇聚为 `RuleTriggerResult` DTO，该 DTO 包含：告警总数、最高命中级别、建议运行状态编码、是否需要维护等字段。随后一次性更新 `eq_device_status` 表的对应字段，避免多次局部更新带来的性能损耗与并发问题。

运行状态升级逻辑遵循以下规则：若命中告警中包含 1 级（紧急）或 2 级（严重）规则，建议状态升级为 3（错误）；包含 3 级（一般）规则时升级为 2（警告）；否则不做升级。

#### 4.2.3 触发时机

状态数据的写入路径（新增与更新）均通过 `EqDeviceStatusServiceImpl.afterSave()` 方法触发评估链路，将规则评估解耦于状态持久化，互不干扰。定时任务（每分钟触发一次）通过 `maintenanceFormService.notifyDevicesRequiringMaintenance()` 对最新一条状态重算规则，保证数据最终一致性。

### 4.3 智能问答与 RAG 模块

#### 4.3.1 Spring AI 集成

系统通过 `spring-ai-alibaba-starter-dashscope`（版本 1.0.0.2）集成阿里云通义大模型。在 `AiConfig` 中注册 `ChatClient` Bean，统一封装模型调用，调用代码示例如下：

```java
String reply = chatClient.prompt()
    .system("你是电力运维领域专家，请结合以下知识库内容回答用户问题。")
    .user(userQuestion)
    .call()
    .content();
```

SSE 流式输出通过 `chatClient.prompt()...stream().content()` 获取 `Flux<String>`，Controller 返回 `SseEmitter`，前端通过 `EventSource` 逐字接收，有效提升交互体验。

#### 4.3.2 RAG 管道设计

RAG 管道包含三个阶段，如图 4-1 所示：

```
[文档上传] ─→ TextReader → TokenTextSplitter → Embedding → SimpleVectorStore (文件持久化)
                              索引阶段

[用户提问] ─→ Embedding → 向量相似度检索 → Top-K 片段 → 拼入 Prompt → ChatClient → 回答
                              检索生成阶段
```

**图 4-1　RAG 管道示意图**

文档切分采用 `TokenTextSplitter`，默认 chunk 大小 800 Token，重叠 100 Token，确保语义连贯性。向量存储采用 `SimpleVectorStore` 文件持久化方案，在无需部署向量数据库的前提下，支持知识库的上传、查询与清空。

#### 4.3.3 知识库管理接口

```
POST /springai/rag/upload-document    上传并索引文档
POST /springai/rag/question           RAG 问答
GET  /springai/rag/question/stream    RAG 流式问答（SSE）
DELETE /springai/rag/clear            清空向量库
POST /springai/rag/generate-form      RAG 增强的运维表单 JSON 生成
```

#### 4.3.4 数据库自然语言查询

`DatabaseQueryService` 将数据库表结构元数据（`eq_*`、`ai_maintenance_form` 等表的列名、类型、注释）拼入系统提示，引导大模型生成正确的 SQL。生成 SQL 后通过安全过滤器（仅允许 `SELECT` 语句，拒绝 `INSERT/UPDATE/DELETE/DROP` 等），再经 `JdbcTemplate` 执行，结果附带大模型摘要（失败时降级为规则化摘要）。接口路径如下：

```
POST /springai/db/ask     自然语言 → SQL → 执行 → 摘要
GET  /springai/db/tables  获取所有表名（辅助前端展示）
```

### 4.4 运维表单业务编排模块

#### 4.4.1 需维护设备列表聚合

`MaintenanceFormService.buildDevicesRequiringMaintenance()` 通过以下步骤聚合设备信息：

1. 查询 `eq_device_status` 中 `maintenance_required=1` 或 `status!=1` 的设备。
2. 查询 `status=1`（未处理）的故障记录，按 `device_id` 合并入 `pendingFaults` 列表。
3. 查询 `status=1`（未恢复）的告警记录，按 `device_id` 合并入 `issues` 列表。
4. 综合规则结果计算优先级（高/中/低）。
5. 可选地调用大模型对各设备生成一句话风险摘要（`aiSummary=true` 时启用）。

前端"问题描述"列仅展示 **待处理故障 + 未恢复告警** 文案，展示层对文本去除英文字母，保证中文整洁呈现。

#### 4.4.2 运维表单 AI 生成

`generateForm()` 方法按以下步骤构建表单：

1. 从故障记录与告警记录中提取要点，形成 `compactFacts` 字符串（剥离「关联数据概览」等冗余段落）。
2. 调用 `summarizeFaultDescriptionAi()`，以 ChatClient 生成 3～6 句专业中文故障描述（禁止条数统计，可换行），失败时降级为规则压缩文本。
3. 通过 `determineMaintenanceType()`、`determinePriority()`、`estimateTime()` 等方法基于规则确定维护类型、优先级和预计耗时。
4. 调用 `generateSteps()` 生成结构化步骤列表（JSON 数组），调用 `generateSafetyPrecautions()` 生成安全注意事项。

批量生成接口 `/ai/maintenance-form/batch-generate` 支持同时处理多台设备，服务端串行调用单台生成逻辑并汇总结果；前端将成功的表单存入 `batchGeneratedForms` 数组，通过 `el-collapse` 折叠列表切换查看，解决批量成功时只展示空白的问题。

#### 4.4.3 表单持久化与历史查询

表单入库调用 `AiMaintenanceFormMapper.insertAiMaintenanceForm()`，并通知站内消息服务。历史记录接口 `/ai/maintenance-form/list` 基于 PageHelper 分页，支持按设备名称、表单状态等条件过滤。

### 4.5 风力发电功率预测模块

#### 4.5.1 GRU 深度学习模型

**GRU（门控循环单元，Gated Recurrent Unit）** 是 LSTM 的简化变体，通过更新门与重置门控制信息流动，在时序预测任务中以更少的参数获得与 LSTM 相近的性能。模型结构如图 4-2 所示：

```
输入序列（时间步=30，特征数=5）
        ↓
GRU 层（16 个单元，return_sequences=True）
        ↓
Dropout（0.2）
        ↓
GRU 层（8 个单元）
        ↓
Dense（1）→ 预测功率
```

**图 4-2　GRU 模型结构图**

输入特征为 30 m、50 m、70 m 处风速与轮毂处风速共 4 个维度，加上功率值共 5 维；时间步长 30（即用前 30 个时间点预测下一时刻）；输出为归一化后的发电功率值。训练使用 Adam 优化器（学习率 0.001）和均方误差（MSE）损失函数，批大小 128，最大轮次 50（配合 `EarlyStopping` 回调），使用 `MinMaxScaler` 对输入与输出分别归一化。

#### 4.5.2 Python 预测服务

预测服务基于 **FastAPI** 框架，提供以下主要端点：

| 端点 | 方法 | 说明 |
|:---|:---:|:---|
| /status | GET | 查询服务状态与模型指标 |
| /train | POST | 异步训练，模型持久化至 model/ 目录 |
| /predict | POST | 加载已存模型进行快速推理 |

`/predict` 接口接收特征 Excel 路径（`feature_excel`）、真值 Excel 路径（`real_excel`）、模型路径（`model_path`）及预测步数（`predict_length`）等参数，读取 Excel 数据后执行滚动预测，返回预测功率序列与可对比的真实功率序列。服务端支持自回归续预测（`beyond_data_points` 参数），在 Excel 数据末行之后再延伸预测若干点。

#### 4.5.3 Java 桥接与配置隔离

Java 侧 `WindForecastBridgeServiceImpl` 通过 Java 内置 `HttpClient` 以 POST 方式调用 Python 预测服务，超时时间可配置（默认 300 s）。预测结果按设备 ID 缓存在内存 `ConcurrentHashMap` 中，`/latest` 接口优先读取缓存，`live=true` 时在当次请求内同步调用预测以保证数据新鲜度。

**设备数据隔离**是本模块的核心设计点。Excel/模型路径的解析优先级为：

```
① 设备绑定表路径（eq_wind_forecast_bind）
② 设备目录下已上传的文件（wind-device-data/{deviceId}/）
③ yml 全局默认（仅当 deviceId == wind.forecast.bind-device-id 时才回退）
```

此机制确保未绑定的设备无法误用全局演示文件进行预测，有效避免多设备数据污染。

预测结果写入 `eq_device_stat`（`remark = 'wind_forecast'`），供统计概览页按时间范围查询展示。预测曲线在前端使用 ECharts 折线图渲染，预测值与实测值以不同颜色区分，同时展示超出 Excel 数据范围的自回归延伸段。

### 4.6 站内消息与推送去重模块

#### 4.6.1 消息表设计

`sys_user_message` 表核心字段包括 `user_id`（接收用户）、`msg_type`（消息类型）、`biz_id`（业务主键）、`read_flag`（读取状态）。当前系统使用两种消息类型：

- `maintenance_form`：运维表单待处理，`biz_id = form_id`。
- `maintenance_device_pending`：待维护设备，`biz_id = device_id`。

#### 4.6.2 去重策略

原有实现存在两类问题：（1）未配置 Redis 时，运维表单推送无去重，每次调用均重复插入；（2）待维护设备同步逻辑每次先删未读再全量插入，用户已读后下一周期仍会再收到新未读消息。

当前实现的去重策略如图 4-3 所示：

```
notifyMaintenanceFormPending(form)
  ├─ 查 countByUserMsgTypeBizId(uid, 'maintenance_form', formId)
  │     若 > 0 → 跳过该用户（数据库级去重）
  │     若 = 0 → 插入
  └─ Redis SET NX (formId, TTL 24h) → 可选防刷

syncMaintenanceDevicePendingMessages(devices)
  ├─ deleteByMsgTypeAndBizIdNotIn('maintenance_device_pending', currentDeviceIds)
  │     清理已不需维护的设备对应消息
  └─ 对每个 (uid, deviceId)
        查 countByUserMsgTypeBizId → 0 时才插入
```

**图 4-3　站内消息去重流程图**

此策略保证：**同一用户对同一业务主键的消息不超过一条**，定时任务每分钟运行也不会重复打扰已读用户。

#### 4.6.3 前端消息中心

消息中心组件（`MessageCenter/index.vue`）通过轮询 `/system/user-message/unread-count` 接口获取未读数，轮询间隔由 `sys_config` 表中 `client.poll.interval.seconds` 参数统一配置（默认 180 s），与发电预测自动刷新间隔保持一致，减少不必要的请求压力。消息列表按创建时间倒序展示，支持单条已读与全部已读操作；点击运维表单类消息可直接跳转至运维表单页面并定位到对应表单。

### 5.2 功能测试

#### 5.2.1 设备规则告警测试

测试用例：为设备 DEV-001 配置"电流大于 200 A 触发告警"规则，随后模拟写入一条电流 = 220 A 的运行状态记录。

**预期结果**：系统自动在 `eq_alert_record` 中插入一条 `alert_level=2`（严重）的告警，设备运行状态更新为"警告"，`maintenance_required=1`。

**实际结果**：与预期一致，告警记录正确生成，设备状态及时更新。重复触发相同规则时，因已有未处理告警，系统不重复入库（去重生效）。

#### 5.2.2 运维表单 AI 生成测试

#### 5.2.3 风力功率预测测试

**预期结果**：绑定设备能正常预测并展示曲线；未绑定设备返回配置缺失提示，不使用全局演示数据。

**实际结果**：与预期一致，数据隔离机制有效。预测曲线中预测功率序列（蓝色）与真实功率序列（橙色）趋势一致，模型效果符合预期。

#### 5.2.4 消息去重测试

模拟定时任务连续运行 10 次（间隔 1 min），验证同一待维护设备是否重复推送消息。

**预期结果**：用户对每台待维护设备只收到 1 条未读消息；设备从待维护列表移除后，对应消息被删除。

**实际结果**：与预期一致，有效杜绝了"消息轰炸"问题。

## 6 结论

本文设计并实现了一套面向电力行业的智能电网运维管理系统。系统在若依框架基础上进行扩展，集成了设备与多维运维数据管理、规则驱动告警与状态联动、基于 RAG 的智能问答与知识库、运维表单 AI 辅助编排、Java 与 Python 协同的 GRU 风力功率预测，以及站内消息业务级去重推送等功能，构建了从数据感知—异常检测—智能辅助—预测预警的完整运维闭环。

系统测试结果表明：规则告警联动准确有效，AI 生成的故障描述专业简洁，风力预测功能完整并具备多设备数据隔离，站内消息去重策略消除了重复推送问题。

本系统的主要创新点体现在以下三个方面：第一，将大语言模型 RAG 能力与传统电网设备运维深度融合，实现知识库增强的智能问答与运维表单自动生成；第二，设计并实现基于 Java 与 Python 异构服务的风力发电 GRU 预测集成，以配置优先级与设备目录隔离解决多设备数据污染问题；第三，提出基于 `(user_id, msg_type, biz_id)` 业务主键语义的消息幂等去重方案，避免定时任务周期性推送对用户造成打扰。

未来工作中，可在以下方向进一步优化：（1）引入更完善的向量数据库（如 Milvus）替换 SimpleVectorStore，提升 RAG 检索性能；（2）对 GRU 模型引入多步预测与置信区间，提高预测可解释性；（3）集成 WebSocket 实现告警的实时推送，进一步缩短响应延迟。
